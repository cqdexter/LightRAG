# LightRAG 检索策略详解

## 概述

当用户向 LightRAG 发起一个问题后，系统经历完整的 **4 阶段处理流程**：关键词提取 → 搜索检索 → 截断过滤 → 合并构建 → LLM 生成。本文档以最推荐的 **mix 模式**为例，逐步解释每个环节。

---

## 一、整体流程总览

```
用户输入问题
    │
    ▼
第1步：关键词提取 ───── LLM 从问题中提取高层关键词和低层关键词
    │
    ▼
第2步：多源搜索 ─────── 根据模式不同，从知识图谱和向量库检索
    │  ├─ local 模式：用低层关键词搜索实体向量库 → 找相关实体 → 找相关关系
    │  ├─ global 模式：用高层关键词搜索关系向量库 → 找相关关系 → 找相关实体
    │  ├─ hybrid 模式：local + global 合并
    │  └─ mix 模式：hybrid + 直接向量检索文本块
    │
    ▼
第3步：Token 截断 ──── 对检索到的实体和关系按 token 上限截断
    │
    ▼
第4步：合并文本块 ──── 轮询合并来自不同来源的文本块（去重）
    │
    ▼
第5步：构建上下文 ──── 将实体描述、关系描述、文本块拼接为 LLM 上下文
    │
    ▼
第6步：LLM 生成回答 ── 将上下文 + 问题发送给 LLM，生成最终回答（支持流式）
```

---

## 二、6 个步骤详细说明

### 第 1 步：关键词提取

**入口函数**：`get_keywords_from_query()` → `extract_keywords_only()`

**做什么**：将用户问题发送给 LLM，要求 LLM 提取两类关键词。

| 关键词类型 | 作用 | 示例 |
|-----------|------|------|
| **高层关键词（hl_keywords）** | 用于 global 模式检索关系，代表问题的宏观主题 | "图书馆规章制度"、"图书借阅" |
| **低层关键词（ll_keywords）** | 用于 local 模式检索实体，代表问题的具体对象 | "办公室电话"、"组织机构" |

**流程细节**：

1. 如果用户在请求中已经提供了 `hl_keywords` 或 `ll_keywords`，直接使用，跳过 LLM 调用
2. 否则构造关键词提取提示词，发给 LLM，要求返回 JSON 格式：`{"high_level_keywords": [...], "low_level_keywords": [...]}`
3. 解析 LLM 返回的 JSON，得到两个关键词列表
4. 将关键词结果缓存到 `hashing_kv`（LLM 响应缓存），相同查询下次直接命中

**关键代码位置**：
- [extract_keywords_only](file:///f:/knowledge_base/LightRAG-1.5.0rc2/lightrag/operate.py#L4010) — 第 4010 行
- [get_keywords_from_query](file:///f:/knowledge_base/LightRAG-1.5.0rc2/lightrag/operate.py#L3880) — 第 3880 行

### 第 2 步：多源搜索

**入口函数**：`_perform_kg_search()`

这是整个检索的核心，根据选择的模式执行不同的搜索路径。

#### 搜索前：批量预计算向量嵌入

在开始搜索之前，系统会将需要用到的问题文本合并为一个批次，一次性调用 embedding 模型计算向量：

| 模式 | 需要嵌入的文本 |
|------|---------------|
| local | 低层关键词 → 用于实体向量库搜索 |
| global | 高层关键词 → 用于关系向量库搜索 |
| hybrid | 低层关键词 + 高层关键词 |
| mix | 低层关键词 + 高层关键词 + 原问题（用于文本块向量搜索）|

这样做避免了多次调用 embedding 模型的往返延迟。

**关键代码位置**：
- [_perform_kg_search](file:///f:/knowledge_base/LightRAG-1.5.0rc2/lightrag/operate.py#L4195) — 第 4195 行

#### 各模式搜索路径

##### local 模式

```
低层关键词向量 → 实体向量库（entities_vdb）搜索 → 找 top_k 个最相似实体
    │
    ▼
获取每个实体的描述、类型等数据
    │
    ▼
根据实体名 → 知识图谱中找出这些实体的所有关联关系
    │
    ▼
返回：local_entities + local_relations
```

**核心函数**：
- [_get_node_data](file:///f:/knowledge_base/LightRAG-1.5.0rc2/lightrag/operate.py#L5014) — 第 5014 行：实体向量搜索 + 获取节点数据 + 节点度数
- [_find_most_related_edges_from_entities](file:///f:/knowledge_base/LightRAG-1.5.0rc2/lightrag/operate.py#L5071) — 第 5071 行：找相关关系

**特点**：以实体为中心，检索与问题最相关的具体实体及其直接关系。适合"某事物是什么？"这类问题。

##### global 模式

```
高层关键词向量 → 关系向量库（relationships_vdb）搜索 → 找 top_k 个最相似关系
    │
    ▼
获取每个关系的描述、权重等数据
    │
    ▼
根据关系中的 src_id / tgt_id → 知识图谱中找出涉及的所有实体
    │
    ▼
返回：global_relations + global_entities
```

**核心函数**：
- [_get_edge_data](file:///f:/knowledge_base/LightRAG-1.5.0rc2/lightrag/operate.py#L5195) — 第 5195 行：关系向量搜索
- [_find_most_related_entities_from_relationships](file:///f:/knowledge_base/LightRAG-1.5.0rc2/lightrag/operate.py#L5275) — 第 5275 行：找相关实体

**特点**：以关系为中心，检索问题宏观主题下的全局关系模式。适合"趋势分析"、"总体概况"这类问题。

##### hybrid 模式

```
  local 路径                          global 路径
    │                                    │
    ▼                                    ▼
  local_entities + local_relations      global_relations + global_entities
    │                                    │
    └────────────────┬───────────────────┘
                     ▼
          轮询合并（round-robin）
                     │
                     ▼
            final_entities（去重后）
            final_relations（去重后）
```

**合并策略**：从 local 和 global 结果中各取一条，交替排列，同时去重（相同实体名或相同关系对只保留第一次出现的）。

##### mix 模式（推荐）

```
  hybrid 搜索逻辑（local + global 合并）
    │
    ▼
  final_entities + final_relations
    │
    ▼
  同时：原问题向量 → 文本块向量库（chunks_vdb）→ 检索 top_k 文本块
    │
    ▼
  vector_chunks（纯向量检索的文本块）
```

**特点**：是 hybrid 的增强版，额外加入了对文档文本块的直接向量检索。这样既利用了知识图谱的结构化知识，又保留了原始文档的上下文信息。这是最推荐的模式。

**关键代码位置**：
- chunks_vdb 检索：[_get_vector_context](file:///f:/knowledge_base/LightRAG-1.5.0rc2/lightrag/operate.py#L4161) — 第 4161 行

##### naive 模式

```
原问题向量 → 文本块向量库（chunks_vdb）搜索 → 直接返回文本块
不涉及知识图谱检索
```

**特点**：最简单的模式，等同于传统 RAG 的向量相似度搜索，不经过知识图谱。

##### bypass 模式

```
跳过所有检索，直接将问题+对话历史发送给 LLM
```

### 第 3 步：Token 截断

**入口函数**：`_apply_token_truncation()`

**做什么**：对第 2 步检索到的实体列表和关系列表，按 token 数量上限截断，确保 LLM 上下文不会超长。

**两个独立的截断**：

| 截断对象 | 上限参数 | 环境变量默认值 |
|----------|---------|--------------|
| 实体上下文 | `max_entity_tokens` | `MAX_ENTITY_TOKENS`（默认 4000）|
| 关系上下文 | `max_relation_tokens` | `MAX_RELATION_TOKENS`（默认 8000）|

**截断算法**：`truncate_list_by_token_size()` — 按 token 大小从前往后保留，超过上限则截断后面的。

**关键代码位置**：
- [_apply_token_truncation](file:///f:/knowledge_base/LightRAG-1.5.0rc2/lightrag/operate.py#L4595) — 第 4595 行

### 第 4 步：合并文本块

**入口函数**：`_merge_all_chunks()`

**做什么**：将第 3 步截断后的实体和关系关联的原始文档文本块，与向量检索的文本块合并。

**三个来源的文本块**：

| 来源 | 说明 |
|------|------|
| **vector_chunks** | 第 2 步中直接向量检索到的文本块（仅 mix 模式有）|
| **entity_chunks** | 基于截断后实体的 `source_id` 关联的文本块 |
| **relation_chunks** | 基于截断后关系的 `source_id` 关联的文本块 |

**合并策略**：三个来源轮询取一条，去重（按 chunk_id），最终生成一个去重后的有序文本块列表。

**每个来源内部选择文本块的策略**（由 `kg_chunk_pick_method` 控制）：

| 策略 | 说明 |
|------|------|
| **WEIGHT（默认）** | 基于文本块被多少个实体/关系引用（出现频次）的加权轮询选择 |
| **VECTOR** | 基于向量相似度选择文本块 |

**关键代码位置**：
- [_merge_all_chunks](file:///f:/knowledge_base/LightRAG-1.5.0rc2/lightrag/operate.py#L4660) — 第 4660 行
- [_find_related_text_unit_from_entities](file:///f:/knowledge_base/LightRAG-1.5.0rc2/lightrag/operate.py#L5100) — 第 5100 行

### 第 5 步：构建 LLM 上下文

**入口函数**：`_build_context_str()`

**做什么**：将实体描述、关系描述、文本块拼接成一段完整的上下文字符串，并进一步按 `max_total_tokens` 截断。

**上下文结构**：

```
-----实体-----
实体名: XXX
类型: YYY
描述: ZZZ

-----关系-----
实体A ←→ 实体B
描述: ZZZ

-----文本块-----
（文档原文片段）
（文档原文片段）
...
```

**最终的 token 控制**：

| 参数 | 控制范围 |
|------|---------|
| `max_entity_tokens` | 实体描述部分的最大 token 数 |
| `max_relation_tokens` | 关系描述部分的最大 token 数 |
| `max_total_tokens` | 整个上下文（实体+关系+文本块）的最大 token 数 |

三个限制同时生效，取最严格的那个。

**关键代码位置**：
- [_build_context_str](file:///f:/knowledge_base/LightRAG-1.5.0rc2/lightrag/operate.py#L4740) — 第 4740 行

---

### 第 6 步：LLM 生成回答

**入口函数**：`kg_query()`

**做什么**：将第 5 步构建好的上下文 + 用户原始问题 + 对话历史（如果有）一起发送给 LLM，生成最终回答。

**系统提示词模板**（`PROMPTS["rag_response"]`）：

```
---角色---
你是一个知识库问答助手。

---上下文---
{context_data}

---要求---
基于以上上下文回答用户问题。
回答格式：{response_type}
用户额外提示：{user_prompt}
```

**支持流式输出**：如果请求中 `stream: true`，LLM 的回答会逐字推送到前端实时显示。

**结果后处理**：去掉 LLM 返回中的提示词部分，只保留纯净的回答内容。

**关键代码位置**：
- [kg_query](file:///f:/knowledge_base/LightRAG-1.5.0rc2/lightrag/operate.py#L3659) — 第 3659 行

## 三、6 种查询模式对比总结

| 模式 | 实体检索 | 关系检索 | 向量文本块 | 适用场景 |
|------|---------|---------|-----------|---------|
| **naive** | ❌ | ❌ | ✅ | 最简模式，纯向量搜索 |
| **local** | ✅（低层关键词） | ✅（实体关联的关系） | ❌ | 针对具体事物的详细查询 |
| **global** | ❌ | ✅（高层关键词） | ❌ | 宏观趋势、主题分析 |
| **hybrid** | ✅ | ✅ | ❌ | 综合知识图谱检索 |
| **mix（推荐）** | ✅ | ✅ | ✅ | 知识图谱 + 向量检索的综合最佳效果 |
| **bypass** | ❌ | ❌ | ❌ | 直接问 LLM，不检索知识库 |

## 四、关键参数说明

| 参数 | API 字段 | 环境变量 | 默认值 | 说明 |
|------|---------|---------|-------|------|
| 检索实体/关系数量 | `top_k` | `TOP_K` | 60 | 每个模式检索的实体或关系上限 |
| 检索文本块数量 | `chunk_top_k` | `CHUNK_TOP_K` | 60 | 向量检索文本块的数量 |
| 实体 token 上限 | `max_entity_tokens` | `MAX_ENTITY_TOKENS` | 4000 | 实体描述最多占用 token 数 |
| 关系 token 上限 | `max_relation_tokens` | `MAX_RELATION_TOKENS` | 8000 | 关系描述最多占用 token 数 |
| 总 token 上限 | `max_total_tokens` | `MAX_TOTAL_TOKENS` | 30000 | 整个上下文最大 token 数 |
| 启用重排序 | `enable_rerank` | `RERANK_BY_DEFAULT` | true | 是否对检索结果进行重排序 |

## 五、数据流备忘

```
用户问题 "图书馆办公室电话"
    │
    ▼
LLM 提取关键词
  hl_keywords: ["图书馆", "联系方式", "规章制度"]
  ll_keywords: ["办公室电话", "图书馆办公室"]
    │
    ▼ (mix 模式)
┌── ll_keywords → 实体向量库 → 找"办公室电话"相关实体
│   └→ 找出该实体的描述和关联关系
│
├── hl_keywords → 关系向量库 → 找"图书馆"相关关系
│   └→ 找出这些关系涉及的实体
│
├── 轮询合并 → 去重的实体和关系列表
│
├── 原问题 → 文本块向量库 → 直接找相关文档段落
│
▼
Token 截断（只保留最重要的）
    │
    ▼
合并文本块（关联的文档段落 + 向量检索的段落）
    │
    ▼
构建上下文 → 发给 LLM → 生成回答
```
